# v0.1 two-host release benchmark — `0f17dca`

This preregistered run establishes the authenticated v0.1 performance claim on
two independent Linux machines: the x86_64 `spider` sender and an ARM64 Raspberry
Pi receiver. All 72 randomized 16 MiB transfers completed and passed end-to-end
SHA-256 verification.

| Criterion | Complete blocks | Estimate | One-sided 95% bound | Threshold | Decision |
| --- | ---: | ---: | ---: | ---: | --- |
| Clean: UDP time / best TCP time | 12 | 0.9679 | upper 0.9944 | <= 1.05 | Pass |
| 1% loss: best TCP time / UDP time | 12 | 2.3274 | lower 1.9303 | >= 1.25 | Pass |

`best TCP` is the faster completed treatment in each block among one TCP stream
and four independent TCP lanes. The evaluator uses the preregistered one-sided
10,000-replicate block bootstrap with seed zero. The matrix used 100 Mbit/s and
20 ms RTT with no injected loss for clean blocks, and 100 Mbit/s, 100 ms RTT,
and 1% forward random loss for lossy blocks.

The sender ran each treatment in an ephemeral rootless Podman container under
`nice -n 10 ionice -c2 -n7`. Netem and the 1,500-byte GSO/GRO cap were applied
only to its private interface; no physical host NIC or qdisc was changed. Blocks
were admitted only when normalized load on both machines was at most 0.75, and
treatment order was randomized within every block. The Pi receiver ran the
cross-compiled static ARM64 binary directly and was reached through `spider` only
for SSH orchestration; transfer traffic used the private Ethernet path.

Revision `0f17dca` incrementally hashes every currently contiguous received UDP
prefix in coarse batches. Packet loss stalls the hash frontier until a repair
fills the gap; completion hashes only the remaining tail. This removes the
serialized full-file hash pass that caused clean-path failure at the previous
revision while retaining final whole-object SHA-256 verification. The 128 MiB
crash regression separately reused 20,406 durable chunks, verified the resumed
file, and completed a retry with zero datagrams.
