# Single-file UDP/TCP/rsync baseline — 2026-07-16

## Outcome

The deliberately simple selective-repeat UDP prototype is already competitive
with TCP on a clean low-RTT path and substantially faster in the tested
high-RTT and random-loss cases. This is a promising result, not yet a general
performance claim.

For a 16 MiB file on a 100 Mbit/s path, the clean-path crossover was between
20 and 30 ms RTT in this implementation:

- 20 ms: UDP and matched TCP were tied at 91.4 and 91.3 Mbit/s.
- 30 ms: UDP was 90.7 versus TCP at 88.4 Mbit/s, a 2.7% advantage.
- 40 ms: UDP was 89.5 versus TCP at 85.5 Mbit/s, a 4.7% advantage.
- 100 ms: UDP was 86.9 versus TCP at 69.0 Mbit/s, a 26.0% advantage.

At 100 ms RTT, the advantage was largest for small and medium files because
the fixed-rate UDP sender did not need to discover the path capacity. It shrank
to 6.1% for a 64 MiB file as TCP amortized slow start.

Random loss produced a sharp, seed-dependent transition for CUBIC. At 20 ms
and 0.1% loss, UDP and TCP were still tied. At 0.2% the UDP median was only
2.2% higher, though one TCP run had already fallen to 71.6 Mbit/s. At 0.3%,
UDP's three runs stayed between 88.3 and 88.9 Mbit/s while TCP ranged from
25.2 to 91.3 Mbit/s; median UDP goodput was 74.5% higher.

At 100 ms and 0.3% loss, UDP delivered a median 70.5 Mbit/s versus 7.8 Mbit/s
for matched TCP. At 1% loss, the medians were 68.3 and 1.8 Mbit/s. Those
loss results are especially preliminary because virtual-link offloads were
not controlled.

## Method

- One Linux host with sender, router, and receiver network namespaces.
- Netem applied the configured rate, half-RTT delay in each direction, random
  loss, and a 10,000-packet queue.
- 100 Mbit/s bottleneck in every first-pass scenario.
- Three deterministic seeds per cell and rotated transport order.
- Sparse zero-filled source on tmpfs; compression disabled.
- Completion required receiver-side file flush and byte-for-byte verification.
- Prototype completion also included receiver SHA-256 verification.
- Every process ran under `nice -n 10 ionice -c2 -n7`.
- 162 measured and verified transfers, excluding smoke tests.

The host was Linux 7.1.3 on an Intel Core i9-13900K. TCP used CUBIC; only Reno
and CUBIC were available. The rsync baseline was version 3.4.4, protocol 32.

## Interpretation boundaries

The matched TCP comparison is the transport result. The rsync comparison is an
application result: its measured interval includes rsync process/protocol setup,
transfer, destination flush, and verification. The prototype interval starts
after its control handshake. Thus the rsync numbers answer “how long did this
fresh single-file invocation take?” but do not isolate TCP itself.

The UDP sender was given the correct path rate. It has no capacity discovery or
adaptive congestion controller yet. That is the intended experiment, but it
means the result applies to provisioned or otherwise known-capacity paths.

The sample count is too small for stable tail estimates under random loss. CUBIC
showed very large run-to-run variation after a loss event, so medians from three
runs should be treated as location hints rather than precise estimates.

Most importantly, `ethtool` was unavailable and GSO/GRO/TSO were not disabled on
the veth links. A netem drop may therefore affect an aggregate rather than one
wire-sized packet. Clean-path and startup results remain useful; random-loss
results need repetition in a lab with offloads explicitly controlled and packet
sizes confirmed by capture.

No BBR result is available because the host kernel exposed only Reno and CUBIC.
No CPU, peak-memory, physical-NIC, shared-congestion, or real-storage conclusion
should be drawn from this pass.

## Next measurement gates

1. Install or otherwise provide `ethtool` in a disposable Linux VM, disable
   virtual offloads, capture packets, and repeat the loss crossover with at least
   10 seeds.
2. Add BBR and a four-stream TCP baseline.
3. Sweep 10, 100, and 1,000 Mbit/s and express file sizes as BDP multiples.
4. Capture CPU time, RSS, socket drops, TCP retransmissions, and qdisc counters.
5. Test pacing at 90%, 100%, and 110% of bottleneck rate and reduce the UDP
   repair tail before considering fountain codes.
